# hcax — 极高压缩率无损归档工具

> 纯 Go 实现的命令行无损压缩归档器。融合 **CDC 去重 + 固实流 + 内容自适应预处理 + 参数自适应 + 上下文混合建模**，
> 对文本/代码/结构化数据的压率**超过 xz / 7z**；对未压缩位图有专门优化。
> **无损 = 字节一致**：解包结果与原文件逐字节相同（已用 `cmp` 逐文件校验）。

## 1. 快速开始

```bash
# 打包（默认 best 模式）
hcax pack 输出.hcax 文件或目录...

# 指定模式
hcax pack backup.hcax ~/Documents -m max

# 解包到目录
hcax unpack backup.hcax ./restore

# 只看内容（-l 显示权限/时间/分类统计）
hcax list backup.hcax -l

# 校验完整性（v6+ 为流级哈希；读老归档时自动退回逐块校验）
hcax verify backup.hcax

# 看归档内部布局（各区占多少字节）
hcax info backup.hcax

# 只抽取其中某个文件（无需全解）
hcax extract backup.hcax ./out report.pdf

# 抽一整个子目录（给目录名即可，抽出整棵子树）
hcax extract backup.hcax ./out src/lib

# 备份时排除 .git / node_modules / 临时文件（可重复给）
hcax pack src.hcax ./proj -m max --exclude .git --exclude node_modules --exclude '*.tmp'
```

**构建**（需要 Go 1.27+）：

```bash
go build -o hcax .
```

## 2. 五种模式怎么选

| 你的数据 | 推荐模式 | 理由 |
|---|---|---|
| **整个文件夹 / 目录树** | **`text`** 或 **`max`** | 元数据一并压缩 + 目录结构完整保留，**压率优于 7z** |
| **文本 / 代码 / 日志 / JSON / 源数据** | **`text`** | 预测式建模，比 xz 再省 8~16% |
| 混合数据，想要**最高压率** | **`max`** | lzma2 极致参数 + 自适应预处理 |
| 超大归档（>64MiB）、想要**速度** | **`max`**（自动并行） | 超阈值自动并行分组，快数倍 |
| 大量**相似文件**、追求速度 | `best` | zstd-19 + 训练字典，快且压率好 |
| 只想**最快** | `fast` | zstd-3 |
| **未压缩位图**（BMP / TGA / PNM-PPM/PGM） | **`text`** > `max` | 自动色彩去相关(RCT)+二维预测(MED)，收益巨大 |
| **已压缩图片/视频**（JPG/PNG/MP4） | `max`（或任意，差别很小） | 已到信息论下限，压不动是正常的 |

**一句话记忆**：
- `text` = 文本/代码专用，最省空间但最慢
- `max` = 通用最强（推荐默认用于归档）
- `ultra` = 去重 + 单流全流选参（极限压率，区别于 `max` 的并行分组；大文件内存与 `max` 同级）
- `best` = 快；进程内 zstd-19 + 训练字典，内存(~230MB)高于 max/ultra(进程外 xz, ~90MB)，是"高 ratio 进程内编码"的取舍
- `fast` = 最快

## 3. 命令参考

### pack — 打包

```
hcax pack <输出.hcax> <文件/目录...> [-m 模式] [--exclude 模式]... [-T]
```

- `-m fast|best|max|ultra|text`（默认 `best`）
- `--exclude <glob>`：可重复。按 完整路径 / 相对打包根的路径 / 任一路径分段 三者
  比对，命中即排除；命中目录时整棵子树跳过（连遍历都省）。例：`--exclude .git`
- `-T` / `--precise-times`：时间戳存到纳秒（会把归档升到 v10，旧版读不了；
  默认按秒存，与 tar 一致）
- 可一次给多个文件/目录，它们会被合并进同一个归档并**跨文件去重**
- 输出会打印：原始大小 → 压缩后大小、压率、模式、唯一块数（可压/原样）
- **目录语义与 tar/zip 一致**：`hcax pack out.hcax dir` 存的是 `dir/a/b/c.txt`，
  解包得到 `out/dir/a/b/c.txt`。打包单个文件时则只存文件名本身
- **符号链接按链接保存**（不跟随、不复制目标内容），解包还原为链接
- **硬链接按硬链接保存**：同一 inode 的多个名字只存一份块索引，解包后重新共享
  inode（只抽其中一个时退化为内容完整的普通文件）
- **不会把自己打进自己**：`hcax pack arch.hcax .` 会自动跳过 arch.hcax
- 权限位含 setuid / setgid / sticky（v10+），mtime 一并还原
- 打包/解包超过 32 MiB 时在 stderr 显示进度；进度不写 stdout，不影响脚本解析

### unpack — 解包

```
hcax unpack <输入.hcax> <输出目录> [--verify]
```

- `--verify`：解包同时校验数据完整性（v6 为流级哈希校验，**可发现归档损坏**）
- 自动重建目录结构（**含空目录**）、文件权限与修改时间。目录的权限与时间是
  **所有条目都写完后再统一补的**——边解边设会被随后的写入冲成"当前时间"，
  提前 chmod 成只读(0555)更会让子文件根本写不进去
- 解到非空目录时会静默改写同名条目（与 tar 同），但会告诉你"覆盖了几条"
- **不会写到解包目录之外**：归档里的名字一律按"相对 + 无 `..`"检查，拼接后再验一次
  前缀；恶意归档用"符号链接 + 链接之下的条目"把文件骗出去的路子也被挡住
  （建目录时逐段检查，挡路的符号链接直接摘掉，见 FORMAT.md §8）

### extract — 随机抽取（不用全解）

```
hcax extract <输入.hcax> <输出目录> [文件名...] [--verify]
```

- 目标可以写 完整路径 / basename / **目录前缀**（给目录名抽出整棵子树）
- 一个都没匹配上会**直接报错**（而不是"抽取完成：0 文件"骗人）；部分没匹配上
  只给警告，命中的照常抽出
- 因为内部是"整体解固实流再按偏移取块"，无需解压全部文件

### list — 列出内容

```
hcax list <输入.hcax> [-l]
```

- 默认按路径排序输出（打包顺序是 文件→目录→链接 三组，直接打印看着是乱的）
- `-l` / `--long`：权限位 + 修改时间 + 链接目标（`->` 符号链接，`=>` 硬链接）
- 汇总行给出 文件 / 目录 / 链接 的分类计数与总量

### info — 容器布局

```
hcax info <输入.hcax>
```

打印版本、模式/后端、条目与块的构成，以及头部/元数据/数据区/原样区/字典区/尾部
各占多少字节。配合 FORMAT.md 用来核对格式。

### verify — 校验

```
hcax verify <输入.hcax>
```

校验归档数据完整、未被篡改。v6 为**流级哈希**校验（固实流 + 原样区）；
读取 v5 及更早的归档时自动改为逐块校验。

## 4. 模式详解与实测数据

> 压率 = 压缩后 ÷ 原始 × 100%，**越小越好**。数据来自本机实测。

### 4.1 混合语料（12.3 MB：文本 / JSON / Go 源码 / 结构化二进制 / 随机 / 未压缩 BMP）

| 模式 | 压率 | 说明 |
|---|---|---|
| **text** | **26.74%** | 🏆 此语料里文本类占比高，CM 略胜 |
| **max** | **26.86%** | 通用最强（与 text 差 0.1%，但快得多） |
| ultra | 26.86% | 整文件固实 |
| best | 32.58% | 快档 |
| fast | 39.65% | 最快档 |
| — | — | — |
| `xz -9e` | 28.00% | 对照 |
| `7z -mx=9` | 28.39% | 对照 |
| `zstd -19` | 28.70% | 对照（单流，未做去重） |
| `zip -9` | 34.27% | 对照 |

**`max` 领先 xz 4.0%、领先 7z 5.4%。**
（语料里那两张 BMP 只有 125 KB，却贡献了好几个百分点——未压缩位图是 hcax 的
强项，见 §4.3；去掉它们后各模式的差距会缩小。）

### 4.2 文本 / 代码（CM 的强项）

| 样本 | **text** | xz -9e | 7z-PPMd | 7z-LZMA2 |
|---|---|---|---|---|
| 小说 774KB | **24.97%** | 29.46% | 23.65% | 29.46% |
| 源码 34KB | **30.33%** | 33.34% | 29.57% | 33.43% |
| 打散重复 768KB | **25.64%** | 30.53% | 24.54% | 30.52% |
| 混合文本 842KB | **22.98%** | 27.10% | 21.83% | 27.10% |

**`text` 比 xz 省 13~16%**，逼近 PPMd（差 3~5%）。
注意"打散重复"那行——**长距离重复被完全破坏后依然领先 13.6%**，说明它靠的是"预测"而非"找重复"。

### 4.3 未压缩位图（BMP / TGA / PNM 专项优化，v7 重写）

**支持格式**：BMP（BI_RGB 8/16/24/32 位，含顶向下）、TGA（类型 2/3，8/24/32 位）、PNM（P5/P6，maxval≤255）。

**两级可逆变换**（纯算法，逐字节 mod 256，可逆）：

1. **RCT 色彩去相关**——彩色图三通道高度相关（R≈G≈B），先换成 `(G, R−G, B−G)`。
   两个差通道几乎恒为 0，直接消掉一大块冗余。**这是本次最大的单项收益。**
2. **MED 中值边缘预测**（LOCO-I / JPEG-LS 的预测器）——用左、上、左上按**边缘方向**预测，
   在边缘处不会越过边界，比"左+上−左上"梯度更稳、比 Paeth/平均更准。

> 变换是**候选制**：打包时用门控实际比较「不变换 / MED / RCT+MED」，**只采用确实更小的**，绝不退步。
> 变换与逆变换都跨块生效（预测依赖整幅几何），因此记在**文件级**（`fe.xform`），不是块级。

**v12：改成逐行运算，跳过 BMP 的行尾填充。**
BMP 每行要补齐到 4 字节；24bpp 且 `宽 % 4 ∈ {1, 2}` 时行跨距不是 3 的倍数
（例如宽 101 → 每行 303 字节像素 + 1 字节填充，跨距 304），旧的扁平实现沿**整块缓冲区**
每 3 字节切一组去做色彩去相关，于是把填充和下一行头两个字节拼成一个"像素"：
通道相位逐行漂移，MED 的"上 / 左上"邻居落到别的通道上，**竖直预测彻底失效**，
结果比不做色彩去相关还差（实测差 60%，门控只能退回到"只做 MED"）。
逐行版只在每行前 `宽 × bpp` 字节内运算，填充保持原样。

**实测（v11 → v12，宽 101 的 24bpp + 32bpp 照片 BMP，共 126 KB）**

| 模式 | v11 | **v12** | 提升 |
|---|---|---|---|
| `fast` | 29,605 B | **28,205 B** | **−4.7%** |
| `best` | 24,975 B | **23,360 B** | **−6.5%** |

无行填充的图（宽为 4 的倍数、或 32bpp）两种实现结果**完全相同**，所以没有回归风险。

**实测（v6 → v7）**

| 文件 | 原始 | v6 `max` | **v7 `max`** | **v7 `text`** | 提升 |
|---|---|---|---|---|---|
| 真实照片 color.tga | 1.19 MB | 79.44% | **61.38%** | **58.87%** | **+22.7%** |
| 真实照片 color.ppm | 1.19 MB | 79.46% | **61.40%** | **58.87%** | **+22.7%** |
| 真实照片 big.bmp | 1.19 MB | 67.37% | **61.38%** | **58.87%** | **+8.9%** |
| 真实照片 pic.bmp | 1.82 MB | 23.58% | **20.75%** | **19.29%** | **+12.0%** |
| 32 位带 alpha BMP | 1.62 MB | 48.51% | **46.32%** | 46.58% | +4.5% |
| 灰度 TGA / PGM | 405 KB | 72.80% | **71.56%** | **69.57%** | +1.7% |

**原理小结**：`RCT` 消掉通道间冗余，`MED` 消掉空间冗余，剩下的残差交给后端压。
图片用 `text`（CM 后端）通常还能再省 2~3 个百分点。

### 4.4 混合语料（含已压缩图片，1.99 MB）

| 模式 | 压率 |
|---|---|
| text | 65.95% |
| ultra | 67.48% |
| max | 67.56% |
| best | 69.45% |

### 4.4b 文件夹 / 目录树（v6 重点优化）

实测语料：一个含 880 个文件的目录树（600 个相似 JSON 配置 + 200 个日志 + 80 个源码 + 子目录结构），共 748 KB。

| 方案 | 归档大小 | 压率 |
|---|---|---|
| **hcax text** | 52,792 | **7.06%** 🏆 |
| **hcax max** | 55,888 | **7.47%** |
| `7z -mx=9` | 58,134 | 7.77% |
| `tar.xz` | 78,948 | 10.55% |
| hcax max（v5 优化前） | 117,976 | 15.77% |

**文件夹场景做了什么**：

1. **元数据一并压缩**：v5 及以前，块表与文件表是**明文**存放，大量小文件时能占归档 **54.7%**；现已随数据一起压缩（同一后端）。
2. **块表精简**：去掉可推导的块偏移（顺序累加即得）；块级哈希改为**流级校验**（每块 8B 随机哈希完全不可压，880 块就是 7 KB 白送）。块表从 31 B/项降到 **5 B/项**。
3. **目录结构完整保留**：空目录也会被记录并在解包时重建（v5 及以前会丢空目录）。
4. **路径修复**：修掉一个长期存在的 bug——绝对路径的公共根在拼接时丢失开头的 `/`，导致 `filepath.Rel` 失败、**所有嵌套路径被拍平成文件名**。现在 `config/a.json` 会正确解包到 `config/a.json`。

### 4.5 大语料并行提速

142.5 MB 语料（可压数据 74.8 MB）：

| 配置 | 耗时 | 压率 |
|---|---|---|
| 并行（≥64MiB 自动启用） | **8.52s** | 32.81% |
| 强制单线程 | 36.75s | 32.41% |

**提速 4.31×**，压率代价仅 +0.40pp。

### 4.6 大文件打包内存优化（v8）

v7 在打包**高度重复的大文件**时（如本机 350MB+ 重复语料），`max` 模式峰值 RSS 高达 **~1.58 GB**，
10 核机上甚至 ~1.33GB，极易 OOM。v8 定位并修复了根因：

**根因**：门控 zstd 编码器（仅用于"估算每块是否值得压"）被创建成
`zstd.WithWindowSize(1<<spec.window)` = `1<<27` = **128 MiB** 的流式编码器，
其历史缓冲 `ensureHist` 在分块过程中膨胀到 **~1.79 GB**（pprof 堆采样占 live heap 的 98.6%）。
门控只需做压率估算，根本不需要大窗口。

**修复**（三处，压率与无损均不变）：
1. 门控窗口从 128 MiB 降到 **1 MiB**；
2. 块缓冲复用 `sync.Pool`，消除每块 `make(64K)` 的瞬时 GC 峰值（GOMAXPROCS 越高越明显）；
3. 去重前置（重复块跳过昂贵预处理）+ 分块/分桶后及时释放 `cm.data`。

**实测对比（367061536B 重复语料，GOMAXPROCS=8，同机同文件）**

| 指标 | v7 | v8 | 变化 |
|---|---|---|---|
| `max` 峰值 RSS | ~1579 MB | **77 MB** | ↓ ~20× |
| `max` 压率 | 0.08% | 0.08% | 不变 |
| `max` 无损 | OK | OK | 不变 |
| `ultra` 峰值 RSS | ~1750 MB | **88 MB** | ↓ ~20× |
| `ultra` 压率 | 0.08% | 0.08% | 不变(去重后反而更好) |
| `ultra` 无损 | OK | OK | 不变 |

> `best`(~264MB) 峰值内存来自 zstd-19 字典训练常驻，保持原状。
> `ultra` 原 v7/v8 早期峰值 ~1750MB 来自"整文件固实且**不去重**"——全部原始块数据必须同时驻留内存（双份）。
> v8b 起 `ultra` 改为**开启去重**（与 `max` 同），仅保留"单流全流选参"的压率优先策略（区别于 `max` 的并行分组），
> 峰值 RSS 降到 **88 MB**（与 max 同级），压率 0.08% 不变。
>
> **别家也这么大吗？是的，甚至更大。** `ultra` 用的就是 lzma2 大字典引擎（同 7z），
> 实测 `xz -9e dict=256MiB` 压同文件 RSS **2974 MB**、解压 **609 MB**；7z 后端真实内存也是 ~3GB
> （只是 `/usr/bin/time -l` 只测到 7z 前端 3MB，真正压缩在子进程里 time 不统计）。
> hcax 之前的 1750MB 是 Go 侧"不去重→双份原始数据驻留"自己的锅，不是 lzma2 固有——去重后这块消失。
> 复现基准见 `bbench.sh`（`./bbench.sh 大文件`）。

### 4.7 进一步内存/健壮性优化（v8c）

v8c 在 §4.6 基础上继续收紧内存，并修掉一个**大文件数据损坏回归**：

**A. 修复 `max` 模式大语料（可压数据 ≥64MiB）解包越界 panic（数据损坏）**
- 根因：v8 的 `cm.data = nil`（及时释放块数据）后，`max` 的并行分组压缩 `compressMT` 仍直接读 `c.data`
  来拼每组数据 → 读到空组 → 产出**空固实帧**（归档里 `compLen=0`）→ 解包时 `readChunk` 对空 `compSolid` 切片越界 `panic`。
- 这条路径只在"可压数据 ≥64MiB 触发并行分组"时走到，**重复语料（去重后 <64MiB）测不出**，故 v8/v8b 漏网。
- 修复：`compressMT` 改为从**保留的 `compSolid` 缓冲**按 `c.offset` 取数据（零拷贝切片），不再碰已释放的 `cm.data`。
- 实测：331MB 非重复语料（`max`）打包→解包→`cmp` **逐字节无损 OK**（修复前 `panic`/FAIL）。

**B. 并行分组零拷贝 + 每组自带字典（降低 `max` 大文件内存/系统内存）**
- 零拷贝：同组块在 `compSolid` 中本就连续，直接取一段切片当组输入，省去"固实流全量 + 各组副本同时驻留"的翻倍内存
  （331MB 非重复语料 Go RSS **2782 MB → 1900 MB**）。
- 每组自带 lzma2 字典：`dictFor(组大小)` 而非整条 `compSolid` 的字典 —— 并行期每个 `xz` 子进程内存随组大小线性下降
  （256MiB 字典≈3GB/进程 → 组字典 64MiB≈700MB/进程，约 **4× 下降**；xz 帧自描述，格式不变）。

**C. zstd 档（best/fast）内存收紧**
- 编码器窗口封顶 **1 MiB**：zstd 按块编码（块上限 256KiB），块内匹配用不到更大窗口，原 `1<<27=128MiB` 窗口纯浪费内存。
- `best` 的**无字典编码器惰性创建**：`best` 总会训练字典并用 `zEncDict`，原 `zEnc`（无字典）从未被使用却常驻一个 level-19 编码器
  （~30MB），改为首次需要时再建 → `best` 峰值 **264 MB → 233 MB**。
- 字典训练样本封顶 **64 MiB**：非重复多文件场景下，原上限 `2000×128KiB=256MiB` 会在训练期与 `cm.data` 双份常驻，封顶后无压率损失。

**v8c 实测（367061536B 重复语料，GOMAXPROCS=8，逐字节无损 `cmp` 校验）**

| 模式 | 峰值 RSS | 压率 | 无损 |
|---|---|---|---|
| `fast` | 42 MB | 0.12% | OK |
| `best` | 233 MB | 0.13% | OK |
| `max` | 89 MB | 0.08% | OK |
| `ultra` | 93 MB | 0.08% | OK |

> `best` 的 233MB 主要是 **Go 堆 arena 随 GOMAXPROCS 放大** + 进程内 zstd-19 编码器（~34MB，由 level 决定、与窗口无关）；
> `max`/`ultra` 把 lzma2 压到**子进程 xz**，Go 侧只留 ~90MB。这是"高 ratio 进程内编码"与"低内存子进程编码"的固有取舍。

### 4.8 固实流落临时文件（v8e）—— 大文件打包内存有界

v8c 把固实流/原样区留在**内存缓冲**（`bytes.Buffer`），整条固实流 = 全量输入常驻。对**非重复大文件**（去重无效），
331MB 语料下 `fast` 峰值 RSS 仍 ~1.8 GB（≈5× 输入）—— 输入的每一字节在内存里同时存了"块切片 + 固实缓冲 + 原样缓冲"多份副本，
且 `bytes.Buffer` 翻倍增长 + GC 惰性不归还 OS 又放大 2~3×。

**根因定位**（数据驱动，`HCAX_T` 埋点 + 堆画像）：
- `fast`（纯 zstd、无 xz）峰值也 1.8 GB → 内存瓶颈**不在后端**，在 Go 侧"整条固实流常驻"。
- `GOGC=20` 把 `fast` 从 1641MB 降到 1134MB → 确认 ~500MB 是 GC 惰性垃圾，但仍有 ~1× 输入的活数据（固实+原样缓冲）。

**修复**：打包阶段固实流/原样区**改写为临时文件**（`os.CreateTemp`），块变换后立即写入文件并丢弃；压缩时**从临时文件流式读取**：
- zstd 档（`fast`/`best`）：`compressZstdStream` 逐段读文件喂 zstd 编码器，内存只留"单块 + 编码器状态"；
- lzma2 并行分组（`max`）：`compressMT` 每组按偏移 `ReadAt` 从临时文件取各自切片（一次 copy，仅组大小常驻），不再持有全量固实流；
- lzma2 单流（`ultra`/中小）：把固实流读回内存（仅 <64MiB，安全）；
- 流级哈希 `hashReader` 从文件流式计算，不再把全量数据读进内存。
- 解包路径**不变**（仍一次性解压固实流到内存），本优化只针对**打包**峰值内存。

**v8e 实测（331MB 非重复多样语料，GOMAXPROCS=8，逐字节无损 `cmp` 校验）**

| 模式 | v8c 峰值 RSS | v8e 峰值 RSS | 降幅 | 压率 | 无损 |
|---|---|---|---|---|---|
| `fast` | ~1866 MB | **380 MB** | ↓ 4.9× | 25.90% | OK |
| `best` | ~2100 MB | **515 MB** | ↓ 4.1× | 25.16% | OK |
| `max` | ~1900 MB | **694 MB** | ↓ 2.7× | 20.73% | OK |
| `ultra` | ~1848 MB | **1096 MB | ↓ 1.7× | 20.62% | OK |

> `ultra` 仍偏高（~1.1GB）：它是"整文件固实、不去重、单流 lzma2"，需把整条固实流读回内存再压——这是 7-zip 式
> 单流极限压率的固有代价，与 v8b 的设计取舍一致；`max` 的 694MB 主要是 8 个 `xz` 子进程（各 ~64–80MB）并行。
> 重复语料（去重有效）各项内存不变（见 §4.7 表）：`fast` 39MB / `best` 235MB / `max` 80MB / `ultra` 82MB。

### 4.9 解包侧内存有界 + 正确性/健壮性修复（v9）

v8e 只把**打包**侧内存修好了，解包侧仍是"整条固实流 + 原样区一次性解进内存"，
且 `openArchive` **无条件**解压 —— 于是 `list` 列个目录也要吃掉全量数据的内存，
`extract` 抽一个 10 字节的小文件同样要把整条流解压一遍。v9 把解包侧补成与打包侧对称。

**改动**

1. **固实流惰性解压 + 落临时文件**：只有真正要读某个块时才解压，且解压结果写临时文件，
   `readChunk` 用 `ReadAt` 取——内存从"全量输入"降到"单块 + 编码器状态"。
2. **原样区零内存**：不解压，直接从归档文件按偏移 `ReadAt`。
3. **抽取提前终止**：`extract` 先算出目标文件块的最大偏移，解压到那里即停
   （抽归档前部的文件不必解完整条流）。
4. **临时文件不再泄漏**：`fatal()` 走 `os.Exit`，Go 的 `defer` 不会执行，
   自 v8e 起打包一旦中途失败，两个临时文件（可达数百 MB）就永久留在 TMPDIR。
   改为显式注册的清理钩子，正常与失败两条路径都会执行。
5. **目录结构不再被拍平**（数据损坏级 bug）：归档根原先取"**文件**的公共父目录"，
   当目录里的文件全部位于子目录中时（如 `src/main/go/*.go`），根被推到 `src/main/go`，
   该层之上的目录全部退化成 basename —— `src/main/go/main.go` 存成 `main.go`，
   且 `go/` 这一层彻底消失。改为取"**输入参数**的公共父目录"，与 tar/zip 一致。
6. **符号链接**：旧实现把链接当普通文件读——指向目录的链接会让 `Read` 返回 EISDIR
   直接打包失败；指向文件的链接则把目标内容复制一份进归档。现按链接保存（v9 格式）。
7. **合法文件名不再被误杀**：路径检查原为 `strings.Contains(name, "..")`，
   会把 `a..b.txt`、`..weird.txt` 这类合法名判成路径穿越攻击，
   表现为"能打包、解不开"。改为逐段判断，只拒绝真正逃逸的路径。
8. **防"先建链接再写穿"**：解包写文件前先摘掉已存在的同名符号链接
   （否则归档里先建 `x -> /etc` 再写 `x/passwd` 会写到解包目录之外）。

**实测（150 MB 非重复混合语料，`fast`，逐字节 `cmp` 无损）**

| 操作 | v8e | **v9** | 变化 |
|---|---|---|---|
| `list`（只需元数据） | 582 MB | **6 MB** | ↓ 97× |
| `extract` 单文件 | 670 MB | **35 MB** | ↓ 19× |
| `unpack` 全量 | 582 MB | **35 MB** | ↓ 17× |
| `pack` | 366 MB | 354 MB | 持平（本次未改打包路径） |
| 抽归档**前部**文件的解压量 | 全条流 | 到目标块末尾即停 | 2.4× 提速 |

压率无回归（12 MB 混合语料）：fast 41.32% / best 33.91% / max 27.47% / ultra 27.47% / text 27.16%，与 v8e 逐位一致。

## 5. 技术原理

按数据流顺序：

1. **内容定长分块（CDC / FastCDC gear hash）**
   按内容边界切块（平均 64KB），相同内容产生相同块 → 支持**跨文件去重**。

2. **去重**
   相同块只存一份。多版本/多副本文件收益巨大。

3. **内容自适应预处理**（每块自动选，取实际更小者）
   - `DELTA`：一维差分（8/16/24/32 位）
   - `BCJ-x86`：x86 可执行文件跳转地址变换
   - `RCT + MED`：未压缩位图（BMP/TGA/PNM）的**色彩去相关 + 中值边缘预测**（文件级，候选制选取）
   - 全部**纯 Go、可逆、字节一致**

4. **不可压判定 + 原样存储**
   图片/随机数据这类压不动的块直接原样存（省时间）。
   判定用"廉价编码器 + 字节熵"双条件，避免把"块内不可压但整体可压"的图像残差误判。

5. **固实流 + lzma2 极限参数**
   可压块拼成一条固实流，一次压缩（吃满跨块冗余）。
   lzma2 参数精调并按数据量自适应：`dict` 按量收敛、`pb` 在 2/4 间实测选优。

6. **并行固实分组**（`max`，可压数据 ≥64MiB 时）
   分 G 组并行压，快 4 倍余，压率略损。

7. **打包顺序聚类**：固实流把所有文件拼成一条，于是"相邻的块是什么"直接影响压率。
   按 扩展名 → 大小量级 → 路径 排序，让同类文件挨在一起（12MB 混合语料：
   fast -0.21% / best -0.15% / max·ultra -0.10%；文本与随机交替的语料 fast -0.9%）。
   `text`(CM) 不走这套 —— 实测重排后反而差 7.2%，它的模型是沿流自适应的。

8. **上下文混合（CM）后端**（`text`）
   不找重复，改为**逐 bit 预测**：order-0~6 上下文模型 + 匹配模型 + 自适应混合器 + 两级 SSE，
   交二值算术编码器。对文本/代码远超 LZ 系。

**容器**：`HCAX` 魔数 + 头 + 数据区（固实帧 + 原样区）+ 块表 + 文件表 + 尾部校验。

## 6. 归档格式

- 当前版本 **v12**，可读 **v2 ~ v12**（向后兼容）
- **版本按需升级**（能不升就不升，每升一版都意味着旧版二进制读不了）：
  普通归档写 v8；含符号链接写 v9；含 setuid/setgid/sticky 或时间戳超出 uint32 秒写 v10；
  加 `-T/--precise-times` 也写 v10（时间戳存到纳秒）；含硬链接写 v11；
  含逐行光栅变换（打进了未压缩位图）写 v12。
  高版本归档被旧版读取时报"版本不兼容"——**明确失败，不会解出错误数据**
- 布局：头部(48B) → **压缩的元数据帧** → 固实数据帧 → 原样区 → 训练字典区 → 尾部
- **元数据（块表 + 文件表）会一并压缩**（v5 及以前为明文，大量小文件时占归档一半以上）
- 块表 **5B/项**：原长(4B) + 标志(1B，含原样/变换类型/字典)。**块偏移不存**——固实流与原样区内块都是顺序紧凑排列，解包时累加即得
- **校验为流级**：固实流、原样区各存 8B 哈希，`verify` 校验整条流
  （读 v5 及更早的归档时自动退回逐块 16B 哈希校验）
- 文件表精简（mtime 4B / mode 2B，v10 起为 8B 纳秒 / 4B 完整权限位），且**目录条目单独记录，空目录不丢**
- **特殊权限位不再丢失**：v10 起 setuid / setgid / sticky 一并保存（v9 及以前用 `FileMode.Perm()`，只取了 0777）
- **v7 新增**：文件表标志位的 bits1–4 = `xform`——记录该文件的**文件级光栅变换**
  （不变换 / MED / RCT+MED / v12 起的逐行 MED / 逐行 RCT+MED）。
  读 v6 及更早的归档时该字段缺失，退回"看到 BMP 就按旧版梯度预测逆变换"的启发式；
  **v7 起不再使用启发式**（否则"故意不做变换"的文件会被误逆变换）。
- **v8 修复（大文件内存爆涨）**：门控 zstd 窗口 128MiB→1MiB + 块缓冲 `sync.Pool` 复用 + 去重前置 +
  分块/分桶后及时释放 `cm.data`。`max` 模式打包 350MB+ 重复语料峰值 RSS 从 **~1.6GB 降到 ~80MB**，
  压率与无损完全不变（详见 §4.6）。

## 8. 性能与限制

### 速度（参考，12.46MB 结构化语料）

本机实测（Apple Silicon，12.6 MB 混合语料：英文文本 / JSON / Go 源码 / 结构化二进制 /
随机数据 / 24bpp+32bpp 未压缩 BMP）：

| 模式 | 打包 | 解包 | 峰值内存 | 归档大小 |
|---|---|---|---|---|
| fast | 0.33s | 0.01s | 102 MB | 4.99 MB |
| best | 1.31s | 0.02s | 316 MB | 4.10 MB |
| max | 5.88s | 0.77s | 92 MB | 3.38 MB |
| ultra | 3.84s | 0.76s | 92 MB | 3.38 MB |
| text | 6.80s | 5.68s | 323 MB | 3.37 MB |

（`text` 是逐 bit 上下文建模，慢是固有的；它赢在压率，不赢在速度。
数字随机器与语料变化，量级比绝对值更有意义。）

### 限制（诚实说明）

1. **已压缩数据压不动**：JPEG/PNG/MP4/随机数据接近熵极限，无损前提下无法再压。
2. **`text` 模式慢**：逐 bit 建模，约 0.5~1 MB/s，适合文本类、不适合大二进制。
3. **CM 对高熵数据无用**：`text` 请只用于文本/代码/日志；二进制用 `max`。
4. **内存**：`text` 约 40~60MB（模型表）；`best` 约 260MB（zstd-19 字典训练常驻）；`max`/`ultra` 约 88MB（去重后同级，v8 前高达 ~1.6GB/~1.8GB）；其余 lzma2 模式解压需 lzma2 dict 工作内存（~dict 量级，与本机 xz 一致）。
5. **未压缩位图限制**：BMP 仅支持 BI_RGB 无压缩、8/16/24/32 位；TGA 仅类型 2/3 的
   8/24/32 位无调色板；PNM 仅 P5/P6 且 maxval ≤ 255。带调色板、RLE 压缩、16 位以上
   每通道的图都走通用路径（不识别，也不做光栅变换）。

### v12 已知未做（诚实清单）

1. **符号链接自身的 mtime 无法还原**：Go 标准库没有 `lutimes`，只能还原普通文件/目录的时间。
2. **不保存 owner / ACL / 扩展属性（xattr）**：只还原权限位与 mtime（v10 起含 setuid / setgid / sticky）。
3. **去重无内容二次校验**：块去重只用 128-bit 哈希，碰撞概率约 2⁻⁶⁴ 量级，理论上存在但实践中可忽略。
4. **无加密、无分卷、无增量更新**。
5. **`text` 模式仍慢**（约 2 MB/s，比 LZ 系慢一到两个数量级）：这是逐 bit 上下文建模的固有代价。
6. **默认丢弃亚秒时间戳**：为不跟旧版二进制绝缘，时间戳按秒存（同 tar），需要纳秒请加 `-T`。

（v9~v12 期间已补齐、不再属于"未做"的：符号链接、硬链接、setuid/setgid/sticky 权限位、
打包侧 `--exclude`、解包侧内存有界、写盘失败不再静默截断、逐行光栅变换（BMP 行填充）。）

## 9. 常见问题

**Q：为什么图片压不动？**
A：JPG/PNG 内部已是熵编码结果，接近信息论下限。无损 + 字节一致的前提下，无法进一步压缩（除非引入外部编码器复现机制，代价大且不可靠）。

**Q：`text` 和 `max` 哪个更小？**
A：看数据。文本/代码选 `text`（小 8~16%）；含二进制/已压缩数据选 `max`。

**Q：解包需要装 xz 吗？**
A：不需要。解压全程纯 Go。只有 `max` 的**压缩**会用到系统 `xz`，没有也会自动回退。

**Q：归档能跨平台吗？**
A：能。格式与字节序明确，`hcax` 是静态二进制。注意文件路径分隔符按打包时记录。

**Q：怎么确认归档没坏？**
A：`hcax verify 文件.hcax`，或解包时加 `--verify`。

**Q：`_legacy_prototype/` 是什么？**
A：项目早期（Python 原型阶段）的产物备份。确认无用后可整体删除，不影响 `hcax`。
